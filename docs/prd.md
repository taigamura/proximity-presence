## Problem Statement

I want an iOS app that quietly tells me when someone from my friends list is within roughly 1km, without revealing who, without a map, and without any chat. Existing apps (Find My, Zenly, Snap Map) do the opposite: they emphasize identity and precise location. I want only the *fact* of presence, delivered as a calm, ambient, meditative reminder that someone I know is out there. Presence as weather, not as an alert.

## Solution

A privacy-first iOS app, "Proximity Presence," built on the same stack and architecture as my existing `simple-bookkeeping` (Kaji) app for maintenance alignment. The client periodically uploads only a coarse geohash-6 bucket plus an ephemeral rotating token. A self-hosted server matches buckets across friend edges and sends a rate-limited, batched silent push that surfaces a single anonymized line: "someone you know is nearby." No name, no map, no history, nothing to tap. Public App Store launch is the target, which adds a compliance workstream on top of the build.

## User Stories

1. As a user, I want to add a friend by sending them an invite link, so that we can connect without exchanging phone numbers.
2. As a user, I want to accept a friend's invite link with a shared secret, so that only intended people become friends.
3. As a user, I want to be notified when a friend is within ~1km, so that I feel a quiet reminder someone I know is near.
4. As a user, I want the notification to never reveal which friend it was, so that presence stays anonymous.
5. As a user, I want no map and no location of the other person, so that the experience stays meditative rather than surveillance-like.
6. As a user, I want notifications capped to roughly one per hour per friend, so that the app feels ambient and never pesters me.
7. As a user, I want near-simultaneous matches batched into one message, so that I get calm signals rather than bursts.
8. As a user, I want notifications to stay off until I have at least a minimum number of friends, so that a ping can't be trivially de-anonymized.
9. As a user, I want the app to work in the background when closed, so that presence is detected without me opening it.
10. As a user, I want honest permission prompts explaining why background location is needed, so that I can trust the app.
11. As a user, I want low battery impact, so that I keep the app installed.
12. As a user, I want a "sleeping" graceful state if I deny background location, so that the app degrades honestly instead of breaking.
13. As a user, I want to remove/block a friend, so that I can sever a connection at any time.
14. As a user, I want to delete my data, so that I can leave the service cleanly (GDPR/APPI).
15. As a user, I want a clear privacy policy and honest App Store data label, so that I know what is collected.
16. As a user, I want the server to never store my precise coordinates, so that a breach cannot reveal where I was.
17. As a developer, I want the client architecture aligned to `simple-bookkeeping`'s folder taxonomy, so that maintenance is consistent across my apps.
18. As a developer, I want a background-location spike gating the full build, so that I don't commit to Expo if the trigger is unreliable.
19. As a developer, I want the backend in Node/TypeScript, so that the whole stack is one language.
20. As a developer, I want match logic that is deterministic and testable, so that I can reason about and test it in a harness loop.

## Implementation Decisions

- **Client stack:** Expo (React Native) + TypeScript, aligned to `simple-bookkeeping` (Kaji) folder taxonomy (`domain/store/nav/ui/screens/theme/i18n/platform/`), RALPH/harness workflow, web-first dev loop. Native (iOS) exercised via dev/EAS builds (Expo Go cannot run background location).
- **Gating spike (first step, before full build):** prove `expo-location` background updates + `expo-task-manager` fire reliably when the app is killed on a real device under "Always Allow." If flaky, fall back to a thin native module for *only* the location trigger; RN for everything else.
- **Range primitive:** GPS-based (BLE too short-range for 1km). Client uploads its current geohash-6 cell only; server matches on bucket string-equality. Neighbor-cell (cell + 8 neighbors) match is a known later upgrade, not MVP.
- **Location trigger:** significant-location-change (500m granularity, low battery), not continuous updates.
- **Backend:** self-hosted Node/TypeScript + Postgres + APNs, on a cheap VPS. Identity-blind. Tables: rotating geohash buckets (hourly rotation, TTL'd), friend edges, ephemeral rotating tokens. Match = bucket join across a user's friend edges.
- **Notifications:** deterministic match under the hood; delivery rate-limited to ~1/hour per friend; near-simultaneous matches batched into one message; gated behind a minimum-friends threshold (3-5) before notifications turn on. No stochastic dropping.
- **Friend graph:** invite-link + shared secret only. No phone-number lookup, no Contacts import. Friend edge keyed to rotating tokens, never to phone numbers or a contact list.
- **Message content:** a single sentence ("someone you know is nearby"). No name, no map, no counter, no history log, no badges, sound off by default.
- **Distribution:** public App Store launch. Adds a compliance workstream: blocking/reporting UI (block = remove friend edge), public privacy policy page (mirror Kaji's GitHub Pages pattern), App Store privacy nutrition label, honest purpose strings, consent flow + real data-deletion path.
- **Seams (three):** client ↔ backend HTTP API (`{ephemeralToken, geohash6}` up, silent push down); backend ↔ Postgres; backend ↔ APNs.

## Testing / Validation Decisions

- **Match engine (backend):** unit-test bucket-equality matching, token rotation, rate-limit/batch, and the minimum-friends gate as pure functions on fixture data. Test external behavior (given these buckets + edges, these pushes fire) not implementation.
- **Background-location spike:** validated on a real device by killing the app and confirming a significant-location-change wakes the task and posts a bucket. This is a manual device test, not automated.
- **Client:** jest (jest-expo preset) + tsc --noEmit typecheck, mirroring Kaji's `npm test` / `npm run typecheck`.
- **Privacy invariant test:** assert the server never receives or stores raw coordinates (only geohash-6 strings) and that tokens rotate.
- **Prior art:** reuse Kaji's testing shape (jest-expo, typecheck, Playwright web-regression where a web target exists).

## Out of Scope

- Transceiver / "ask what they're doing" reply mechanic (dropped by the idea as "iffy"; breaks anonymity).
- Any map, precise location display, or friend identity reveal.
- Phone-number lookup and Contacts import.
- Peer-side private set intersection (PSI) crypto: overkill for a small friend graph; server-side anonymized matching is the MVP.
- Neighbor-cell (8-neighbor) matching in MVP (known later upgrade).
- Cross-platform Android launch (iOS-first; Expo keeps Android open later).
- Monetization / analytics / engagement growth features.

## Further Notes

- **Biggest unknown:** iOS background-location + battery discipline. Could double the build estimate. The spike exists to surface this before full commitment.
- **Anonymity is contextual, not cryptographic.** Small friend graphs in quiet areas allow guessing who pinged. Mitigations: minimum-friends threshold; optional future stochastic jitter (explicitly not in MVP).
- **Effort:** ~4-6 weekends to build for a solo builder, + ~1-2 weeks App Store review calendar risk (now in scope because launch is public).
- **Repo:** `proximity-presence` at `/home/taigamura/projects/proximity-presence` (WSL). User will create the repo and run to-issues there.

# Stage-4 research (prior art, risks, sources)

## Problem statement

An iOS app that quietly notifies a user when *someone from their friends list* is within 1km — without revealing who, without a map, without a chat/transceiver. The original framing: *"the user shouldn't know who the friend is. Anonymize whose actually nearby. Instead of showing where the other is, this app is just supposed to be a reminder that theres someone you know out there. A sort of meditative comforting app experience."*

Core loop = one ambient signal, no follow-up action. This is the opposite of Find My or Zenly — those emphasize *identity and location*; this app deliberately removes both, keeping only the fact of presence. Design thesis: presence as weather, not as an alert.

## Prior art found

- **Zenly** (Snap, shut down 2023-02-03) — the canonical friend-map app; ~40M MAUs at shutdown; killed for strategic reasons, not product failure. Reveals identity + precise location. (Source: https://blog.pragmaticengineer.com/zenly/) Opposite design philosophy; useful as a foil, not a template.
- **Apple Find My** — reveals identity + location; requires Apple ID pairing. (Source: https://developer.apple.com/documentation/corelocation/cllocationmanager) Not anonymized; not the same primitive.
- **Snap Map, Foursquare Swarm** — identity-first friend maps; same category, same identity reveal. No anonymized "someone is nearby" mode exists in any of them.
- **Somebody (Miranda July / Miu Miu / Stink Studios, 2014)** — art-project GPS messaging app that routed your text to the nearest *Somebody* user to deliver in person. (Sources: https://mirandajuly.com/somebody-app/ and https://www.stinkstudios.com/work/somebody) Closest ambient/presence prior art; validates that "presence as UX" is a legible design idea, but Somebody revealed identity at delivery.
- **Google/Apple Exposure Notification (COVID protocol)** — BLE-only, server-blind proximity detection with rotating keys; proves the crypto pattern works at national scale. (Source: https://developer.apple.com/documentation/exposurenotification) Wrong range primitive (BLE ~10m, not 1km) but the anonymization pattern is directly reusable.

> No mainstream shipped app currently offers "anonymized friend nearby" as its core loop. That is the gap this idea fills.

## Rough approach

**Range primitive.** BLE (like Exposure Notification) is too short-range for 1km. Must be GPS-based. Two viable architectures:

1. **Server-side proximity with anonymized payloads (recommended MVP).** Each client periodically posts a *geohash bucket* (e.g. geohash-6 ≈ ~1.2km cells) + an ephemeral rotating friend-graph token. Server checks: does any of my friends' current buckets equal mine? If yes → silent push → local notification "someone you know is nearby". Server sees buckets, not identities linked to buckets (rotate tokens hourly). No map, no name is ever displayed client-side.
2. **Peer-side private set intersection (future).** Cryptographic PSI on rotating friend-key sets; server acts only as a relay. Reference implementation exists (https://github.com/contact-discovery/mobile_psi_cpp) but overkill for a small friend graph and adds real complexity.

**iOS constraints (hard blockers to design around).**
- Each app may only monitor **20 geofences** via CLRegion (Source: https://radar.com/blog/limitations-of-ios-geofencing). Cannot geofence around N friends' live positions client-side. Must invert to *upload my location bucket, let server do the match*.
- Background location needs **"Always Allow"** — a well-known friction point; iOS re-prompts. Onboarding must earn this permission.
- Use significant-location-change updates (500m granularity, low battery) as the update trigger, not continuous updates.
- Purpose strings must be honest ("to tell you when a friend is nearby without revealing who").

**UX principles (from ambient/slow-tech lineage).**
- Single-glance UI: one sentence ("someone you know is nearby"), no map, no counter, no history log.
- No badges. Sound off by default.
- Deliberate latency — batch notifications to feel like weather, not alerts. Cap at ~1/hour per friend to avoid pestering.
- No reply/transceiver mechanic (already dropped by the idea as "iffy" — keep it dropped; it breaks the anonymity guarantee).

**Stack sketch.** SwiftUI + CoreLocation client. Server: small Go or Node service, Postgres (buckets, friend edges, rotating tokens), APNs for silent push. A cheap VPS covers MVP scale.

## Effort estimate

**~4-6 weekends** to a private TestFlight for a solo Swift-fluent builder, dominated by:
- iOS background-location permission dance and battery tuning (biggest unknown; could easily double the estimate).
- Server-side geohash matching + token rotation (~1 weekend, well-understood).
- Onboarding + friend-add flow (invites via link + shared secret) (~1 weekend).
- Meditative UX polish (deceptively hard — it is *supposed* to look like nothing).

App Store review is a separate ~1-2 week calendar risk on top of build time.

## Open questions

- Does the user have Swift/iOS experience, or would this be a learning-from-zero project? Choice of native SwiftUI vs. cross-platform (Flutter/React Native) hinges on this — but background-location + battery discipline strongly favor native. **Needs human decision.**
- Bootstrap friend graph: invite-link only (SMS/AirDrop) vs. phone-number lookup vs. optional Contacts import? Each has a distinct privacy footprint. Not resolved.
- What counts as "nearby"? Literal 1km circle, or geohash-6 bucket (~1.2km, but rectangular)? The user's "1km" is likely approximate — bucket accuracy is fine for meditative UX.
- Should notifications be *deterministic* (fire every time someone enters range) or *stochastic* (some presences pass silently) to reinforce the weather metaphor?
- Monetization / distribution intent: personal art project, gift for friends, TestFlight-only, or App Store? Answer changes the shape of the build.

## Risks

- **iOS "Always Allow" permission cliff.** Users may deny background location outright. Without it, the app cannot function. Mitigation: excellent onboarding storytelling; graceful "sleeping" state when denied.
- **Battery / thermal complaints.** Continuous location is the #1 App Store review complaint for this genre. Must use significant-location-change, not continuous updates.
- **App Store rejection risk.** Guideline 1.1.6 (fake trackers), 5.1.1 (data-collection consent), 5.1.2 (data-use limits) all apply. Anonymization *helps* the review story (no identifiable friend data leaves device). Social apps also need blocking/reporting under 1.2 — trivial here since users can only add friends they invite. (Source: https://developer.apple.com/app-store/review/guidelines/)
- **GDPR + Japan APPI.** Location data is personal data; needs freely-given, specific, informed consent, purpose spec, retention limits. (Source: https://plainlawguide.com/eu/data-privacy/gdpr-location-tracking) Bucket-only storage with hourly rotation makes compliance much easier than storing precise coordinates.
- **The meditative UX might not be "sticky".** By design there is nothing to *do*. Retention could be very low. That may be the point (art project), or may be a business-model dead end — depends on user's intent.
- **Small friend graphs = probabilistic identity leak.** If the user has only 3 friends and gets a "nearby" ping in a quiet neighborhood, they can often *guess* who it was. Anonymity is contextual, not cryptographic. Consider minimum-friends threshold before enabling notifications, or add stochastic jitter.
